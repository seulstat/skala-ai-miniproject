# 발표 대본 — Interview Coach Agent

> 슬라이드 6장, 약 5분 30초(4쪽이 길어짐). 각 슬라이드의 **발표자 노트**에도 같은 대본이 들어 있습니다.
> 시간이 부족하면 2쪽은 문제 세 가지 제목만, 6쪽의 다음 단계는 한 문장으로 줄이면 5분 안에 들어옵니다.

## 1. 표지 (약 20초)

제가 만든 서비스는 ‘Interview Coach Agent’입니다. 10/13에 설계했던 영어 면접 답답노트 Agent를 웹 서비스로 확장한 것인데요, 내 서류와 공고에서 근거를 찾아 영어 표현 카드를 만들고, 검수를 거친 뒤 제가 승인한 것만 복습 카드로 쌓는 흐름은 그대로 가져왔습니다.

## 2. 10/13 버전의 문제 → 이번 해결 (약 40초)

지난 버전은 동작은 했지만, 매일 쓰기에는 세 가지가 걸렸습니다. 첫째, 터미널에서만 돌아가고 승인 대기 중인 카드가 메모리에만 있어서 프로그램을 끄면 사라졌습니다. 둘째, 검수 노드가 생성과 같은 그래프 안에 있다 보니 검수가 생성 쪽 맥락에 끌려가는 경우가 있었습니다. 셋째, 실패했을 때 왜 실패했는지 알 수가 없었습니다. 그래서 각각 웹 서비스와 DB 저장, 생성과 검수 에이전트 분리, 4계층 오류 처리로 풀어봤고, 오른쪽 숫자는 같은 모델로 다시 측정한 결과입니다.

## 3. 핵심 흐름 · 실행 화면 (약 50초)

전체 흐름은 위와 같습니다. 준비 탭에 서류와 공고를 넣고 질문을 보내면, 내 문서에서 근거를 찾아 카드 초안을 만들고, 별도의 검수 에이전트가 확인해서 필요하면 최대 두 번까지 다시 쓰게 합니다. 그다음 제가 승인한 카드만 저장되고 복습으로 이어집니다. 아래는 OpenAI로 실제 실행한 화면입니다. 첫 번째는 문장 표현 요청으로, 진행 단계가 실시간으로 표시되고 카드 아래에 근거 출처가 붙습니다. 두 번째는 면접 질문으로, 제 경험을 바탕으로 30~45초 분량의 답변 초안이 나옵니다. 세 번째는 카드 탭인데요, 승인한 카드 두 장이 다음 복습일과 함께 저장된 것을 확인할 수 있습니다.

## 4. 아키텍처 · 기술 요소 (약 100초 — 그림의 ①~⑨ 번호를 따라 시선 이동)

다음은 아키텍처입니다. 그림의 번호 순서대로 따라가 보겠습니다. 1번 브라우저는 사용자가 보는 화면으로, 질문을 보내고 진행 상황을 실시간으로 받습니다. 2번 web_server는 화면 파일을 보내 주고, 브라우저의 요청을 뒤쪽 서버로 그대로 전달해 주는 중간 다리 역할을 합니다. 3번 server.py가 실제로 요청을 처리하는 API 서버인데요, 위쪽 data 폴더에 프로필과 경험 문서, 공고를 저장하고 읽어 옵니다. 질문이 들어오면 아래 4번 Supervisor 그래프가 어떤 요청인지 분류하고 전체 순서를 지휘합니다. 표현을 만들어야 하면 오른쪽 5번 Coach에게 초안을 맡기는데, Coach는 필요한 근거를 스스로 골라서 위쪽 6번 MCP 서버에 검색을 요청합니다. MCP 서버에는 Tool이 두 개 있는데요, 내 경험 문서에서 관련 문단을 찾아 주는 search_my_experience와, 면접 표현집에서 비슷한 상황의 표현을 찾아 주는 search_expression_bank입니다. 공고 내용과 검수 규칙도 이 서버에서 받아 옵니다. 초안이 나오면 오른쪽 7번 Reviewer가 검수하고, 문제가 있으면 Coach에게 되돌려 최대 두 번까지 다시 쓰게 합니다. 검수를 통과하면 다시 Supervisor로 돌아와 제 승인을 기다리는데, 이때 그래프가 멈추고 그 상태가 아래 8번 checkpoints.db에 저장됩니다. 그래서 새로고침하거나 서버를 다시 켜도 승인 대기 카드가 복원되고, 승인하면 왼쪽 coach.db에 카드가 저장됩니다. 맨 아래 9번은 실제 AI 모델로, 점선이 모델을 부르는 부분입니다.

오른쪽은 이 구조가 기술 요소의 어디에 해당하는지 정리한 것입니다. 멀티 에이전트는 4, 5, 7번이고, MCP와 RAG는 6번, HITL은 8번입니다. 의존성 주입은 모델이나 MCP 연결, DB 같은 부품을 3번 서버가 켜질 때 한 번만 만들어서 그래프에 넘겨주는 방식인데요, 덕분에 테스트할 때는 이 부품만 가짜로 바꿔 끼울 수 있습니다. 그래서 실제 AI 대신 정해진 답만 하는 가짜 모델로, 인터넷 연결 없이 테스트 179개를 돌렸습니다. 개발은 코어, MCP, API, 화면 네 가지 역할로 나눠서 병렬로 진행했습니다.

## 5. Before / After (약 60초)

결과를 살펴보겠습니다. 같은 모델과 같은 테스트 10건으로 두 버전을 세 번씩 돌려 비교했습니다. 카드 생성 성공률은 81%에서 100%가 됐고, 서버를 다시 켰을 때 승인 대기 카드 복원은 0건에서 3건 모두로 바뀌었습니다. 요청 두 개를 처리하는 시간은 동시 처리 덕분에 절반 정도로 줄었고, 개인 맥락 점수는 거의 그대로 유지됐습니다. 그리고 측정하는 과정에서 지난 버전이 실패한 원인도 찾을 수 있었는데요, 검색 횟수 제한이 카드를 내보내는 마지막 호출까지 막아서 무한 반복이 생겼던 것이었습니다. 10/13에는 Gemini를 써서 이 문제가 드러나지 않았습니다. 그래서 이번 버전에서는 제한에 닿으면 검색 도구를 아예 숨겨서 카드만 낼 수 있도록 고쳤습니다.

## 6. 한계 · 트레이드오프 (약 50초)

마지막으로 한계입니다. 첫째, 검수를 분리하면서 검색과 재작성 횟수가 늘어 카드 한 장에 2초 정도 더 걸립니다. 둘째, 개인정보 때문에 로컬 모델로도 돌릴 수 있게 해 두었는데, 같은 10건에서 qwen3 8b는 카드를 한 장도 만들지 못했고 qwen3.5 4b는 일곱 건 중 다섯 건만 성공했습니다. 셋째, SQLite를 써서 대화마다 약 121KB씩 쌓이고, 사용자 한 명과 서버 한 대까지만 지원합니다. 넷째, OpenAI를 쓰면 서류가 외부로 전송됩니다. 다음 단계로는 검색 횟수 조정, 요청과 관련된 카드 복습, PostgreSQL 전환, LangSmith 평가 자동화를 생각하고 있습니다. 마무리하겠습니다. 미루던 영어 면접 준비를, 이제는 믿고 매일 쓸 수 있는 서비스로 만들었습니다. 감사합니다.

## 예상 질문

- **왜 멀티 에이전트로 나눴나요?** 지난 버전에서는 검수가 생성과 같은 상태를 보면서 생성 쪽에 끌려가는 경우가 있었습니다. 그래서 검수를 별도 에이전트로 떼어 냈고, 에이전트를 셋 이상으로 더 나누는 건 호출 수와 일정 부담이 커서 두 개로 정했습니다(ADR-0004).
- **MCP는 왜 따로 프로세스로 띄웠나요?** 서류와 공고 같은 데이터 접근을 MCP 경계 뒤로 숨기려고 했습니다. 처음엔 프로세스를 나누면 느려질까 걱정했는데, 측정해 보니 호출당 1ms 정도라 지연의 원인은 아니었습니다(ADR-0003).
- **왜 PostgreSQL이 아니라 SQLite인가요?** 이번 범위는 사용자 한 명이라 SQLite로 충분하다고 판단했고, 여러 서버에서 공유가 안 되는 점은 한계로 남겨 두었습니다(ADR-0006, 0008).
- **사람이 승인하면 실시간 흐름이 끊기지 않나요?** 매 응답마다가 아니라 저장 직전에만 승인을 받고, 생성과 검수 과정은 그대로 실시간으로 보이도록 했습니다(ADR-0006).
- **테스트셋을 왜 바꿨나요?** 기존 10건은 제 실제 경력을 전제로 한 문장이라, 개인정보 때문에 가상 인물 서류로 바꿨습니다. 구성 비율은 그대로 맞췄습니다(ADR-0009).
- **오류가 나면 사용자는 어떻게 되나요?** 오류마다 코드와 안내 문구가 정해져 있어서, 다시 시도하면 되는 오류는 ‘다시 시도’ 버튼을, 서류가 없으면 준비 탭으로 가는 버튼을 보여 줍니다. 근거 검색 하나가 실패해도 카드는 계속 만들고 경고만 띄웁니다(ADR-0012).
