# ADR-0003: RAG를 MCP 서버 프로세스 안에 둔다

- 상태: Accepted
- 날짜: 2026-10-20
- 작성: Lead
- 관련: design.md §2 "RAG 위치", §3 RAG 행

## 배경
10/13 버전은 Agent 프로세스 안에서 경험 문서를 임베딩하고 검색했다(`dapdap/rag.py`).
웹 서비스에서는 문서를 업로드 API(A3)가 쓰고, 검색은 MCP Tool이 맡는다. 임베딩·캐시·재색인을 어느 프로세스가 맡을지 정해야 했다.

## 결정
RAG(제목 단위 분할 → 임베딩 → 코사인 검색)는 MCP 서버 "coach" 프로세스 안에서 수행한다. 10/13 `rag.py`를 재사용한다.
문서 파일의 mtime이 바뀌면 재색인한다. 결과에는 `[파일 > 제목]` 출처 라벨을 붙인다.

## 대안 비교
| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| Agent(FastAPI) 프로세스 안 RAG(10/13 방식) | 왕복 없음 | 데이터 접근이 Agent·MCP 양쪽에 흩어짐, MCP Tool이 껍데기가 됨 | MCP 경계의 의미가 약해짐 |
| 별도 벡터 DB(Chroma 등) | 대용량에 강함 | 의존성·운영 부담, 문서 수 개 수준에 과함 | MVP 범위 초과 |
| 키워드 검색만 | 단순, 임베딩 비용 없음 | RAG 요구사항 미충족, 한↔영 의미 검색 약함 | 평가 기준 미충족 |

## 결과
- 긍정: 데이터 접근이 MCP 경계 뒤로 숨는다. Agent는 출처 라벨이 붙은 텍스트만 받는다.
- 부정(트레이드오프): MCP 서버가 임베딩 모델 설정(`EMBEDDING_MODEL`)을 알아야 한다. 첫 호출에 색인 지연이 생긴다. 서버 재시작 시 캐시(`embedding_cache.json`)에 의존한다.
- 후속 조치: A2가 `rag.py`의 `.config` 의존을 `DataPaths`·`EMBEDDING_MODEL`로 교체하고, 테스트용 fake 임베딩을 둔다.
- 검증 방법: A2 테스트 — 출처 라벨 포함, mtime 변경 시 재색인, Resource 섹션 추출.
