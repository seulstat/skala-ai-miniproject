# ADR-0010: 역할 분담과 worktree 병렬 진행

- 상태: Accepted
- 날짜: 2026-10-20
- 작성: Lead
- 관련: work-plan.md §2·§6, design.md §9, agent.md §2

## 배경
2.5일 안에 에이전트 코어·MCP·API·프론트를 모두 만들어야 한다. 여러 agent가 한 작업 트리에서 동시에 고치면 충돌과 "남의 파일 수정"이 생긴다.
설계 단계에서 테스트 7(복습 단계 전환)은 Day2 오후로 잡혀 있었지만, 카드 store는 A1이 Day1 저녁에 만든다.

## 결정
Lead + 역할 4개(A1 코어, A2 MCP·RAG, A3 API, A4 프론트)로 나누고, 역할마다 `feat/<role>` 브랜치와 `.worktrees/<role>` worktree에서 자기 경로만 수정한다.
역할 사이 접점은 `contracts/`에 코드로 고정하고, CP0~CP4에서 core → mcp → api → web 순으로 병합한다. CP를 통과하면 private 레포 `origin`에 push한다.
테스트 7은 store를 만드는 A1의 완료 기준에 포함하고 CP1(Day2 오전)까지 끝낸다.
원본 참고 파일은 `ref/`에 읽기 전용 복사본으로 둔다.

## 대안 비교
| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| 단일 agent 순차 진행 | 충돌 없음 | 일정 안에 끝나지 않음 | 일정 |
| 브랜치만(worktree 없이) 병렬 | 디스크 절약 | 브랜치 전환 때 작업 중 파일·venv가 섞임 | 동시 실행 불가 |
| 계약 없이 병렬 | 착수 빠름 | 통합 시점에 인터페이스 불일치 폭발 | 통합 위험 |
| 테스트 7을 Day2 오후(A3 이후)에 | 원 설계 유지 | store 담당(A1)과 검증 시점이 어긋남 | 담당자와 완료 기준 불일치 |

## 결과
- 긍정: 역할이 병렬로 진행되고, 소유권 위반은 `check.sh` ⑤가 기계적으로 잡는다. 계약 fixture로 A4는 백엔드 없이 개발한다.
- 부정(트레이드오프): 계약 변경은 Lead를 거쳐야 해서 느리다. worktree마다 `.venv`가 필요하다. ADR 번호가 브랜치끼리 겹칠 수 있다(CP에서 재번호).
- 후속 조치: CP마다 Proposed ADR 확정, 사용자 리뷰 게이트.
- 검증 방법: CP0에서 main과 worktree 4개 모두 `check.sh` 통과, CP1에서 테스트 1~7 통과.
